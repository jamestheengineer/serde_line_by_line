# Decisions

Architecture decisions with the evidence behind them. Recorded so a future
change has to argue with the measurement, not with a preference.

Measurements taken 2026-08-18 on rustc 1.95.0, against the pinned
`serde_core-1.0.229` tree (19 files, 12,037 lines, 361.9 KB).

---

## D1 — WASM: `wasm-bindgen`, one shared playground module

**Decision:** use `wasm-bindgen` (pinned exactly), compiling all examples into a
single playground module that dispatches by id. Not raw `wasm32-unknown-unknown`.

### Measured

Same example (`ok_and_error`), `opt-level = "z"`, LTO, stripped, one codegen unit:

| approach | .wasm | gzipped |
|---|---:|---:|
| raw `wasm32-unknown-unknown`, manual ptr/len ABI | 41.8 KB | **18.3 KB** |
| `wasm-bindgen` | 56.0 KB | **22.9 KB** |

**The real difference is 4.6 KB gzipped.**

### Why bindgen wins anyway

The raw ABI has to hand a `String` across the boundary by hand: leak it into a
static, return a pointer, expose a length accessor, and have JS read linear
memory. The minimal version of that does not even compile clean:

```
warning: creating a shared reference to mutable static
  --> src/lib.rs:18:14
   |
18 |     unsafe { LAST.as_ref().map_or(0, |s| s.len()) }
   = note: shared references to mutable statics are dangerous; it's undefined
           behavior if the static is mutated ...
```

Getting that right means a hand-rolled unsafe allocator protocol. This project
exists to teach correct Rust; shipping a bespoke unsafe FFI shim to save 4.6 KB
is the wrong trade, and it is 4.6 KB *once*, not per example, because all
examples share one module.

### Cost accepted

`wasm-bindgen` the crate and `wasm-bindgen-cli` must be the **same version** or
the build fails. Mitigation: pin `wasm-bindgen = "=0.2.127"` in Cargo.toml and
install the matching CLI explicitly in CI. This is the standard practice and the
failure mode is a loud, clear error rather than a subtle one.

### Rejected

- **`wasm32-wasip1` + a WASI shim**, which would let examples `println!`. It
  reintroduces a JS shim, and examples returning `String` is already required so
  the same code can run under `cargo test`.

## D2 — Highlighting: syntect at build time, class-based, per-annotation span

**Decision:** pre-render highlighted HTML at build time with `syntect`
(`default-features = false, features = ["default-fancy"]` — pure Rust, no
`onig` C dependency), emitting **CSS classes**, at **per-annotation-span**
granularity rather than whole files.

### Measured

Highlighting the entire crate takes **1.6–2.1 s**, so this is comfortably a
build-time step and would even survive being done per-request.

Output size, for the worst case (`de/impls.rs`, 3,173 lines, 94.9 KB source):

| approach | HTML | gzipped | notes |
|---|---:|---:|---|
| inline `style=` (`styled_line_to_highlighted_html`) | 620 KB | — | 5.7× source; colors baked in, no theming |
| classed, one generator **per line** | 1,585 KB | 50.2 KB | 13.7× source; scope stack re-emitted every line |
| classed, one generator **per file** | 1,237 KB | 35.8 KB | **1,595 of 3,174 lines have unbalanced spans** |
| **classed, per 10-line annotation span** | **3.8 KB** | **0.5 KB** | what the app actually renders |

### The finding that decided it

Whole-file rendering is the wrong question. The three-pane reader shows one
annotation's span beside its explanation — roughly ten lines. At that
granularity the output is **3.8 KB**, and the verbosity of a per-line generator
stops mattering entirely.

That also sidesteps a real trap: with a single generator per file, syntect lets
spans cross line boundaries, so **half the lines cannot be split apart without
producing malformed HTML**. Per-span generation is self-contained by
construction, which matters because annotations are line-range keyed and every
line needs to be independently addressable.

### Why classes rather than inline styles

Inline `style=` bakes one theme into the markup. Classes plus a stylesheet give
light and dark themes from the same generated HTML, which the reader app needs
anyway. Slightly larger raw, irrelevant after gzip, and far more flexible.

## D3 — Delivery: static site generator, with Askama templates and an Axum dev server

**Decision:** the app is a **static site generator** (`cargo xtask build-site`)
using **Askama** templates, plus a small **Axum** dev server for local
iteration. Not a live server in production.

### Why

Nothing in the design needs a server at request time:

| capability | resolved by |
|---|---|
| running examples | D1 — WASM, entirely client-side |
| syntax highlighting | D2 — precomputed at build time |
| annotation content | static data, read-only |
| coverage / progress | `coverage.json`, generated by CI |

A live backend would exist only to serve bytes. Static deployment means no
hosting cost, no ops, no runtime attack surface, and GitHub Pages serves `.wasm`
with the correct `application/wasm` type out of the box. CI already builds
everything needed.

Askama is kept because it is the templating half of the choice already made in
PLAN.md §3, and it works identically whether the HTML is written to disk or to a
socket. Axum survives as a dev-only convenience: a few dozen lines serving the
output directory with live reload, so the write-and-refresh loop stays fast.

### Consequence for the roadmap

Phase 1 gets simpler: no request handlers, no state, no deployment target beyond
"push and let CI publish". The remaining phase-1 risk is entirely in the reader
UX, which is where it belongs.

## D5 — CI is enforced before the push, not after it

**Decision:** `.githooks/pre-push` runs the same gates as
`.github/workflows/ci.yml` and blocks the push if any fail. Enabled per clone
with `git config core.hooksPath .githooks`.

### Measured

Of the eleven runs before this was added, seven failed. Every one of them failed
on the same gate, `cargo fmt --all --check`, and the last seven failed on the
same two lines: an import list in `examples/num_widening/src/lib.rs` that was
committed unsorted and then pushed seven more times before anyone ran `cargo
fmt`.

| | |
|---|---:|
| runs before the hook | 11 |
| red | 7 |
| distinct causes | **1** |
| distinct causes that were not `cargo fmt` | **0** |

The full gate set, warm, on this machine:

| gate | time |
|---|---:|
| Format | 0.15 s |
| Clippy | 0.26 s |
| Examples | 1.4 s |
| Coverage, Build site | ~1 s |
| wasm job | ~10 s |

### Why a hook and not more CI

CI already reported all seven failures correctly and promptly. It was not a
detection problem — the red X was there each time, and the next commit was
pushed on top of it anyway. Nothing failed except the feedback arriving after
the push, when acting on it costs a context switch instead of two seconds.

Moving the identical commands to just before the push converts a build-status
notification into a blocked action, which is the only form of the feedback that
cannot be deferred. It also costs a couple of seconds, which is cheap enough
that no one is tempted to route around it; `--no-verify` stays available for
the deliberate case.

### What it does not cover

A hook narrows the gap; it does not close it. The runner has a newer stable
toolchain than this machine on any given day, so a fresh `clippy` lint can still
land red on a push that was green locally. The wasm gates are skipped, loudly,
when the local `wasm-bindgen` does not match the pin in `playground/Cargo.toml`.
Neither has actually broken a run yet, but "never fails" is not a promise a
pre-push hook can make — it is a promise about the class of failure that has
happened here, which is the entirely preventable one.
